## 1. Чем отличается Git от GitHub?

Git — это инструмент для управления версиями проекта. Он фиксирует изменения в файлах, позволяет работать с историей проекта, создавать отдельные ветки и объединять результаты разработки.

GitHub, в отличие от Git, является онлайн-сервисом. На нём размещаются удалённые Git-репозитории, благодаря чему участники проекта могут получать изменения друг друга, создавать Pull Request и совместно работать над кодом.

Таким образом, Git отвечает непосредственно за контроль версий, а GitHub предоставляет среду для хранения репозиториев и командного взаимодействия.

## 2. Для чего используется виртуальное окружение Python?

Виртуальное окружение создаётся для того, чтобы зависимости одного Python-проекта были отделены от зависимостей других проектов.

Для каждого проекта можно установить собственный набор библиотек и нужные версии пакетов. Это помогает избежать ситуаций, когда обновление или установка библиотеки для одной программы нарушает работу другой.

В данной практической работе используется окружение `.venv`, внутри которого устанавливаются необходимые проекту библиотеки, например `pandas` и `matplotlib`.

## 3. Что такое commit, branch, remote, pull request?

**Commit** — это сохранение определённого состояния изменений проекта в истории Git. Каждый commit позволяет зафиксировать выполненный этап работы.

**Branch** — отдельная ветка проекта. Она позволяет разработчику выполнять новую задачу, не изменяя напрямую основную ветку `main`.

**Remote** — удалённый репозиторий, с которым связан локальный Git-репозиторий. В данной работе таким удалённым хранилищем является репозиторий на GitHub.

**Pull Request** — запрос на перенос изменений из одной ветки в другую. Перед объединением изменений их можно проверить, обсудить и при необходимости исправить.

## 4. Зачем нужен файл `.gitignore`?

Файл `.gitignore` нужен для исключения из Git тех файлов и папок, которые не должны храниться в репозитории.

Например, нет необходимости загружать на GitHub виртуальное окружение `.venv`, временные файлы, кэш и некоторые локальные настройки среды разработки.

Благодаря `.gitignore` в репозитории остаются только файлы, которые действительно относятся к проекту и необходимы для его разработки.

## 5. Как организовать командную работу над бизнес-приложением с помощью Git?

Перед началом работы участнику необходимо получить актуальную версию основной ветки `main`. После этого для отдельной задачи создаётся новая ветка.

В этой ветке разработчик изменяет необходимые файлы, фиксирует результат с помощью commit и отправляет изменения в удалённый репозиторий через `push`.

Затем на GitHub создаётся Pull Request. Второй участник может просмотреть внесённые изменения, написать комментарий или одобрить их. После проверки выполняется слияние с основной веткой `main`.

После merge участники снова обновляют локальную ветку `main`, чтобы получить общую актуальную версию проекта.

Такой подход позволяет разделять задачи между разработчиками и контролировать изменения перед их добавлением в основную версию приложения.

## 6. Какие файлы обязательно должны быть в репозитории учебного проекта?

Для выполнения данной практической работы в репозитории используются следующие основные файлы:

- `.gitignore` — содержит правила исключения ненужных файлов из Git;
- `README.md` — содержит основную информацию о проекте и инструкцию по его запуску;
- `requirements.txt` — хранит сведения о необходимых Python-библиотеках;
- `main.py` — содержит программный код учебного приложения.

После выполнения домашнего задания в проект также добавляется файл:

- `docs/business_requirements.md` — содержит бизнес-требования к разрабатываемому приложению.

Такая структура позволяет хранить отдельно программный код, описание проекта, зависимости и документацию.

## 7. Что произойдёт, если два разработчика изменят один и тот же файл в разных ветках?

Работа каждого разработчика будет сохранена независимо в его собственной ветке.

При объединении веток Git попробует совместить изменения. Если участники редактировали разные части файла, объединение обычно выполняется автоматически.

Если же изменения затрагивают одни и те же строки, может возникнуть конфликт слияния (`merge conflict`). В такой ситуации автоматическое объединение невозможно, поэтому разработчику нужно вручную проверить оба варианта, выбрать правильное содержимое и сохранить итоговую версию файла.

После разрешения конфликта изменения можно зафиксировать и завершить слияние веток.
